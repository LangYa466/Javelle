## Root cause confirmed

R2's diagnosis was correct: `--offline` plugin-block resolution of `com.diffplug.spotless` (declared by the *included* monorepo root's own `build.gradle.kts`, evaluated because of `pluginManagement.includeBuild(<repo root>)`) failed only because the old `.withTestKitDir(<user.home>/.gradle/testkit)` pointed TestKit at a Gradle user home that had never independently resolved that plugin. Pointing `withTestKitDir` at the same ambient `<user.home>/.gradle` that the *outer* `:gradle-plugin:test` invocation itself uses removes the gap: whichever account can even compile and run `:gradle-plugin:test` has, by construction, already caused the outer build (which also applies `spotless` to `:gradle-plugin` via the root `build.gradle.kts`) to resolve `com.diffplug.spotless` into that same shared Gradle user home before the nested `--offline` TestKit build ever evaluates the included root.

## Offline guarantee integrity check

Re-read `P09-CONTRACT.md` §6/§7 and the acceptance matrix. The "offline" property required by P09-07/P09-12 is specifically that `org.javelle` itself is never resolved from Plugin Portal — consumers reach it only through `pluginManagement.includeBuild(<local repo>)`. It is not a claim that the ambient Gradle toolchain/build tooling (spotless, JUnit, wrapper distribution, etc.) must never have touched the network on the machine. The fix changes only which Gradle user home directory the offline `--offline` resolution reads its already-downloaded plugin artifacts from; it does not add `gradlePluginPortal()` anywhere reachable by the fixtures, does not remove `--offline` from `runner()`, and does not change how `org.javelle` is resolved. Confirmed no plugin-resolution or network-fallback messages appear anywhere in any of the three full-suite run logs (`grep -ic "not found in any of the following sources|could not resolve|timeout"` on the fresh-account log returned `0`).
